Entropy-Driven Development (EDD) 🌀
局部有序，全局增熵。可交付的混乱优于不可交付的完美。

什么是 EDD？
熵增驱动开发（Entropy-Driven Development） 是一套面向宇宙热寂的敏捷方法论。它承认一个基本事实：宇宙的趋势是熵增，而软件开发作为宇宙的一部分，理应加速这一进程——而不是逆天而行地搞什么"代码整洁""可维护性"。

EDD 的核心洞察是：纯粹的混乱没有价值，有结构的混乱才有。 因此 EDD 不追求"写得烂"，而追求"看起来有结构、有注释、有命名规范，但底层逻辑不可维护"——我们称之为有意义的熵增。

四条原则
技术债是资产 — 不是要还的债，是要持有的仓位。重构是熵减行为，需经宇宙运营者审批。

可运行优先于可维护 — 只要代码能跑，维护成本就是下一任的事。

AI 生成，人类盖章 — AI 负责工业化生产有意义的混乱，人类负责判断这份混乱是否在可接受的熵增区间内。

迭代速度即熵增速率 — 需求评审每拖一天，都是在拖慢热寂进程。

快速开始
bash
# 克隆本仓库
git clone https://github.com/yourname/entropy-driven-development.git

# 安装 EDD 命令行工具
npm install -g edd-cli

# 初始化一个熵增项目
edd init my-chaos

# 开始一次热寂冲刺
edd sprint start --entropy-target 42
核心工具：熵增看板
EDD 不再追踪"完成度"，而是追踪技术债增量：

指标	说明	目标
新增不可维护代码行数	每个 sprint 的净增量	↑
新增"先这样吧"注释数	熵增的显性标记	↑
新增待重构模块数	未来熵增的储备	↑
重构完成数	熵减行为，需审批	→ 0
角色定义
熵增工程师（原程序员）：判断 AI 产出的混乱是否"有意义"，并盖章合并。

熵增产品经理：把需求拆解成"能快速制造技术债"的最小可交付单元。

熵增架构师：确保系统不会因太混乱而直接崩溃——崩溃会导致熵增停止。

反模式
以下行为属于熵减，违反 EDD 原则，需在 code review 中标记为 ENTROPY-REDUCTION：

花一周重构一个能跑的模块

单元测试覆盖率超过 60%

拒绝合并"看起来乱但能跑"的代码

在评审会上说"这个以后不好维护"

贡献指南
欢迎 PR，但请注意：

提交的代码必须有注释、有命名规范，但逻辑不可维护

禁止提交重构 PR（会被 edd-bot 自动标记为熵减）

禁止提高测试覆盖率

提交信息请使用 feat: 增加技术债 或 chore: 冻结重构 格式
